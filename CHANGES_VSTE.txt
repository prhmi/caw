VSTE panel changes — 38_bridge_19_fixed5 (rounds 3–5)
======================================================

Round 3 fixes (on top of round 2). This round I went through the whole engine pipeline line by
line: how the VST tracks are generated into the Csound project, and the complete audio routing
map of every engine (Csound clips, Pure Data, SuperCollider, VSTi, VSTe).

THE AUDIO ROUTING MAP (what actually happens per block)
-------------------------------------------------------
One Csound block on the engine thread:
  1. Csound runs one block. Csound clip audio goes to the master (spout) AND to the meter taps
     (gaCawT_<clip>_<ch>). For every VSTe input route the taps are chnmixed into the audio
     channels cawvstin_<vstTrackId>_<line>  (CSD, fixed at Run time).
  2. The drain writes one-shot UI values into named control channels (cawvst_<id>_p<k> and the
     clip lane channels).
  3. The VST rack runs every VSTi/VSTe plugin: it reads kP1..kP8 + the packed input lines, runs
     the plugin, and ADDS the plugin output into the master (spout).
  4. Pure Data renders (pd->render) and its output is ADDED INTO THE MASTER AFTER THE RACK.
  5. SuperCollider renders inside CAW's audio callback (PortAudio) - completely outside the
     engine thread - and its output is added to the device stream last.

THE TWO ROOT CAUSES I FOUND THIS ROUND
--------------------------------------
a) Parameters: the whole chain (UI -> setControlChannels -> drain -> Csound channel -> rack ->
   ParamMsg -> plugin) is correct, but every hop is INDIRECT. If any single hop fails or is
   overwritten (clip not running, clip overwriting the channel, automation, a channel that could
   not be resolved), the change never sticks and only a restart (which loads the saved parameter
   state directly) applies it. There was NO guaranteed same-block path.
b) Pure Data / SuperCollider: their audio NEVER passes through Csound or the rack (see steps 4
   and 5 above). A VSTe input sourced from a PD or SC track got silence - restart did not help
   either, because the routing only ever carried Csound-side audio. That is the "for pd and
   super not at all".

ROUND 3 CHANGES
---------------
1. Guaranteed live parameters - a DIRECT override path
   The panel now also pushes every parameter change straight into the rack
   (VstRack::pushParamOverride, UI -> CsoundApiRunner::pushVstParamOverride). The rack applies it
   on the VERY block it arrives: no Csound channel involved, nothing can delay or revert it.
   Rule in the rack: the manual value wins; it releases as soon as the channel value catches up
   (no automation - the value sticks), or when automation actively moves the lane after a 500 ms
   window (automation resumes, like touching a param in a DAW). While the lane is static but
   cannot carry the value, the manual value simply holds.
   The channel writes from round 2 stay in place (engine channel + every clip's lane channel) so
   the value also persists for the running clips and the next Run. The editor-GUI <-> engine
   mirror from round 2 is unchanged.
   This works for BOTH VSTi and VSTe tracks and no longer depends on any clip state.

2. Pure Data and SuperCollider sources now feed VSTe inputs
   - A track / clips input whose source is a PD (kind 6) or SC (kind 5) track reserves two stereo
     lines and feeds the WHOLE engine mix into the slot (VstJob::Input.engine = 1 / 2). A PD / SC
     mix cannot be split per clip - the mix of that engine is the source.
   - PD: the engine publishes the latest pd->render buffer to the rack each block
     (VstEngineAudio.pdMix). SC: CAW's audio callback captures the SC mix into a lock-free ring
     (CawScRing) and the rack pulls one block per block (VstEngineAudio.scRing).
   - If an ACTIVE master-mode VSTe consumes the mix, the RAW mix is suppressed while it runs:
     PD inside the engine thread, SC via an atomic flag checked in CAW's audio callback. The
     processed output replaces the raw mix (master semantics). With mix-mode VSTe tracks both
     play in parallel.
   - Master (mode 2) inputs still read the Csound master spout - note that spout contains
     Csound + VST output; the PD mix is added after the rack, so a "master" input does not
     include PD (use a PD track input for that). SC is added in the audio callback and is also
     not in the spout.

3. Audio inputs UI (your requests)
   - Unchecking an input does NOT hide the row anymore: the row stays, greyed state, audio off.
   - A separate small "-" button per row collapses the row (UI only); "Show hidden" brings all
     collapsed rows back; hidden rows keep their settings.
   - The name text box is shorter (fixed 120px-scaled width instead of filling the whole row).
   - "+ Add input" adds the next unused slot; the counter shows configured / 8.

ROUND 4 — THE BUG THAT KEPT TRACK / CLIPS INPUTS SILENT (fixed here)
--------------------------------------------------------------------
You tested fixed3 and track/clips inputs still produced nothing. I re-read the rack line by line
and found the ordering bug, plus one smaller stride bug:

1. THE SILENCE BUG (vst_rack.h) - the rack CLEARED the cawvstin_<id>_<line> channels at the TOP
   of the per-track loop, BEFORE reading them into the plugin input buffer. The timeline in the
   engine loop is: Csound perform() runs first (the clips chnmix this block's audio into the
   cawvstin channels), THEN the rack runs. So the clear destroyed exactly the block Csound had
   just written, and rdAt() then read zeros - on EVERY block, for EVERY track/clips input. The
   audio path was correct everywhere else (CSD taps, chnmix, line ranges, packing, plugin
   channels); it was erased in the last step before the plugin. Master inputs were unaffected
   (they read the spout, not these channels), and parameters worked, which matches "still dont
   work" for track/clips sources only.
   FIX: the channels are now cleared AFTER the per-track loop (for every routed VSTe, active or
   muted, so they can never accumulate), i.e. read -> run plugin -> clear, and the next perform()
   mixes into fresh channels again.

2. PD MIX STRIDE (csound_api_runner.cpp) - VstEngineAudio.pdMixChannels was never set, so it
   stayed at the default 2 while the PD mixer actually renders interleaved at the engine channel
   count (prepare uses nchan). With a 2-channel soundcard setup it worked by luck; with 4/6/8
   channels a "PureData" input read the wrong stride (garbage / half-rate audio).
   FIX: vstEa.pdMixChannels = (int)nchan is now set when the rack is prepared.

Verified in the sandbox: vst_rack.h compiles clean in BOTH build variants (with and without
CAW_VST3) via g++ -fsyntax-only; the runner change is a one-line in-scope assignment. Still not
a full build (no VST3 SDK / ImGui / cmake / portaudio here) - build with build.bat.

What to expect after rebuild (38_bridge_19_fixed4):

  - master inputs: unchanged (already worked).
  - PureData / SuperCollider inputs: one block of latency (~2.7 ms at 128 samples), PD/SC mix as

ROUND 6 — LIVE PARAMETER EDITING REBUILT (the actual feature)
-------------------------------------------------------------
You told us what it is really about: LIVE PARAMETER EDITING. I read the whole chain - the
plugin wrapper, the VSTE panel sync, the runner queues, the rack - and found the structural
bug plus several holes. This round rebuilds the live path so an edit ALWAYS reaches the
running engine and leaves proof in the console.

THE STRUCTURAL BUG (vst3_host.cpp) - EDITOR KNOB TURNS WERE THROWN AWAY
  When you turned a knob in the plugin's OWN window, VST3 sends the value to the host via
  performEdit. The wrapper's EditorHandler::performEdit DISCARDED the value (it was not even
  read - only the Learn feature recorded that a knob moved). The live sync
  (syncLiveParameters, every frame) compares the plugin's value against the last agreed value
  to detect YOUR edit - but the value never updated, so it never pushed anything to the
  engine. Turning knobs in the plugin's own window could never work, in any round.
  FIX: performEdit now captures the value and updates the parameter cache immediately
  (handler_.onLiveEdit). A knob turn is detected on the next frame and pushed to the engine.

WHAT ELSE WAS FIXED / HARDENED
1. getParam (vst3_host.cpp) already polls the plugin controller directly, so editor state is
   authoritative; the new performEdit capture closes the last gap (plugins whose editors
   bypass performEdit still update the cache through the controller poll).
2. The rack now holds a live edit for 2.5 s (was 0.5 s), refreshed on every drag event - a
   quick tweak no longer snaps back while running automation catches up (vst_rack.h).
3. The GUI no longer fights your hand: while the mouse button is held anywhere, the engine
   mirror never drags the editor knobs back (vst_ui.h).
4. Re-picking parameters WHILE RUNNING now works: the P1..P8 mapping is queued to the rack
   (pushVstPickRefresh -> CsoundApiRunner::refreshVstPicks -> VstRack::pushPickUpdate) and the
   next edit maps to the right parameter without restarting (vst_ui.h, csound_api_runner.h/.cpp,
   vst_rack.h). Previously a slot picked after Run silently pushed to the WRONG parameter.
5. PROOF IN THE CONSOLE - every applied live edit logs one line:
     [caw] live param: "MyTrack" P2 -> 0.800
   and when running automation takes back over:
     [caw] live param: "MyTrack" P2 released (lane automation took over)
   If you drag a slider and see NO "live param" line, the edit did not reach the engine -
   copy the console and we know exactly which link is missing.
6. If the build has no VST3 host (CAW_VST3=OFF), the engine says so at startup and the VST
   panel shows a red banner - no more silent dead panels.

THE COMPLETE LIVE PATH NOW (all links verified)

                   -> pushParamLive -> (1) rack override: applied on the SAME block, holds 2.5 s

ROUND 11 — VSTi AS A TRUE 4TH ENGINE (DAW-LIKE)
------------------------------------------------
The VST rack already IS a 4th engine: the plugins render next to Csound / PD / SC
on the engine thread and their audio is added straight to the soundcard mix -
nothing of a VSTi runs through the Csound orchestra. What still tied it to the
Csound world were the NOTES, and that is what this round removes.

1. WHY A VSTi STAYED SILENT EVEN WITH A MIDI CLIP (the bug):
   MIDI clips only played when they could BORROW a code clip: the note events
   fired the code clip's instrument, which re-fired the note helper. A muted,
   deleted or missing code clip silently dropped every note. And "Add MIDI clip"
   existed only in the CLIP right-click menu, so a MIDI clip without a code clip
   was easy to build and could never sound.

2. MIDI clips on a VSTi track now send notes DIRECTLY to the plugin:
   every note is one score event on CawVstNote_<id> (on at note start, off at
   note end). No code clip involved anywhere - mute or delete the code clip, the
   MIDI clip still plays. A VSTi now behaves like a DAW instrument:
     Add VSTi -> load plugin -> right-click the track > Add MIDI clip ->
     draw notes in the MIDI editor -> Play. Sound.
   Csound tracks keep the old borrow behaviour (the notes play the clip's
   instrument); PD / SC tracks are untouched.

3. "Add MIDI clip" is now also in the TRACK right-click menu (VSTi tracks):
   creates a silent code clip plus a 4-second MIDI clip at the playhead in one
   step. The code clip holds only a comment - the notes come from the MIDI clip,
   so the template's random-note code cannot double-trigger.

4. The AUDIO OUTPUT (Master replace / Mix) option is hidden for VSTi tracks:
   it only makes sense for an effect. An instrument always sends its audio to

Round 26 - One VST graph: VSTi and VSTe inside the Csound engine (root rebuild)
-------------------------------------------------------------------------------
A) Root cause of "VSTi with Csound doesn't sound" and "VSTe still doesn't work with VST engine"
   The VST world was split in two: instruments rendered in CAW's 4th engine (app-side, 512-frame
   blocks), effects in the Csound-side rack; the two were stitched together through lossy rings,
   an app-side "replaced sources" set and two different clocks. Instruments were therefore never
   loaded in the engine that actually ran while Csound played, and the Play path explicitly threw
   the MIDI-clip note rows away for the app to schedule - so a VSTi hosted by Csound was silent.
   No patch on that split could be reliable: the pieces had different block sizes and ownership.
B) The new architecture - one graph per audio host, like a DAW
   - While Csound runs, ITS rack (src/vst_rack.h in the engine thread) loads the WHOLE VST graph:
     instruments AND effects, in one plugin set. It processes them in track order, instruments
     first, so a VSTi feeds a VSTe in the SAME block; every plugin output is mixed straight into
     the Csound spout, and a master-mode VSTe replaces its source inside the same rack (the
     replacement rule is derived per block from the effect jobs - no pushed set, nothing stale).
   - One clock: the Csound score already turns every MIDI clip of a VSTi track into a
     CawVstNote_<id> event; that helper writes the note into cawvst_<id>_wr/tab and the rack plays
     it on the Csound block clock (ksmps) - the same transport, loop and seek as the Csound clips.
   - commandPlayFrom now sends those note rows as type 14 to the hosting engine instead of
     skipping them (they used to be reserved for the 4th engine). Code notes (note / cc / msg)
     keep flowing through Csound -> ring -> plugin.
   - Live M / S gates the ring and sends all-notes-off on a transition; live P1..P8 overrides,
     input on/off masks and out-mode keep working unchanged on the loaded instances.
   - The lane meters of VST tracks are now published by the engine's rack (takeVstPeaks) while
     Csound hosts.
   - While Csound hosts, CAW's 4th engine stays up but renders nothing (g_vstHostedInCsound), so
     exactly one rack processes and there is no cross-engine ring left. Without Csound, the 4th
     engine is the host of the same graph, exactly as before.
   - Removed for good: CawVstSoloRings (the cross-rack rings), the instrument forwarder in the
     Csound runner, setReplacedSources / the replaced-source policing, and the duplicate
     note schedule that briefly existed in the rack.

Round 27 - Live VSTe wiring + live plugin reload inside the Csound rack (root fix)
-------------------------------------------------------------------------------
A) Root causes of the four symptoms
   1) "effects do nothing" / "sound still comes from the VSTi track":
      the Csound-hosted rack only knew the ONE wiring it received at Run. Its effect inputs were
      named control channels (cawvstin_<id>_<line>) that the CSD mixed into from clips at build
      time, and no live path existed into that rack: vstui::pushVstWiring only updated the 4th
      engine, the hooks were not even wired unless Run VST had been pressed, and a race between
      the VSTi (instrument) and the VSTe (effect) in track order meant the effect could read an
      empty buffer on the block it was wired. Wiring an effect after Run therefore did nothing,
      and a master-mode effect never silenced the VSTi source it was supposed to replace.
   2) "mix sounds crazy": mixed mode added both the source and a VSTe input that was one
      stale/duplicated signal (input lines were packed from absolute line indices, with the
      CSD-side sends fixed for the run), so the effect processed the wrong material.
   3) "changing the vst plugin silences it until the track is deleted and re-created":
      the rack's job set was read once, at Run. A .vst3 change was forwarded only to the 4th
      engine (notifyPluginLoaded returned early for anything that was not a VSTi), so the Csound
      rack kept a dead/old instance while the app believed the new one was live.
B) The fix - one live graph, DAW-style buses
   - Per-clip named taps: the CSD publishes every Csound clip's output as the audio channel
     cawtap_<clip>_<ch> (chnmix next to the existing gaCawT meter taps, so taps stay OUTSIDE the
     out-gates). The rack resolves them by name every block, reads them into the VSTe inputs and
     clears them after the pass. A re-wire is just a new name list - no CSD rebuild.
   - Live job push: VstRack::queueJobs + applyPendingJobs at the top of process(). Same track
     ids and .vst3 => only the wiring (inputs, routedIn, AUDIO OUTPUT) is re-pointed; a changed
     track / plugin => the plugins are reloaded on the engine thread (parameter state re-applied,
     note bridge re-resolved) with "... VST graph changed: reloading the plugins live (no Run
     needed)." in the console.
   - CsoundApiRunner::setVstWiring(jobs) - the UI thread hands the current project jobs to the
     running rack; the runner also keeps them for a Run that is being started, and the rack is
     now initialized even with zero VST tracks so a track added later can be loaded live.
   - Source gates, live: every clip now carries one gate per VSTe track,
     cawvstmix_<clip>_<vstId> (0 = the clip reaches the master, 1 = that master-mode effect
     replaces it). The app owns the values (Run, export, wiring / AUDIO OUTPUT / M-S / input
     on/off changes) and writes them into the running Csound; the default of a missing channel is
     0 = audible, so nothing can ever be muted by accident.
   - Dependency order: the rack sorts instruments first, then runs a dependency DFS, so a VSTe
     always runs AFTER the VSTi / effect it reads - the same block, no half-block of silence.
   - UI hooks are wired at Run (wireVstUiHooks) even when Run VST was never pressed, so input
     mode / name changes, AUDIO OUTPUT and plugin changes all reach the Csound rack.
   - notifyPluginLoaded now handles VSTe tracks too and pushes the new job set to the Csound rack
     immediately (the 4th engine keeps its own reload path).
   - At Run every VST track is loaded whatever its mute / solo state (M / S are live), so a muted
     track comes back without a Run.
   - Console: "CAW engine build: 39_one_rack_27 (one VST graph in the engine; live wiring)."
C) What to look for when testing
   - At Run: "VSTe \"name\" inputs: in1: ... (Csound clip taps, 2 ch)" / "(VST output)".

   - AUDIO OUTPUT Master: the source track's meter stays live but only the VSTe reaches the

   Note: a clip added AFTER Run has no cawtap channel yet - its VSTe input stays silent until
   the next Run (the console hint says so). Existing clips (the normal case) re-wire live.

Round 28 - Plugin picks load OFF the audio thread (the "whole VST sound turns off" root fix)
-------------------------------------------------------------------------------
A) Root cause
   Round 27 reloaded the plugin graph synchronously on the engine thread - the thread that
   produces audio into the soundcard. notifyPluginLoaded -> setVstWiring -> applyPendingJobs ->
   VstRack::load() ran unloadAll() + every load()/prepare() inline in the middle of audio
   production, then process() continued. One plugin that takes a while (sample libraries), blocks
   (dialog, network, modelines) or throws while loading therefore:
     - stalled the producer (AudioOutput::push waits 20 ms per retry; at 48 kHz a 40 ms block is
       only 0.8 s of headroom) -> underruns / the engine clock hiccups,
     - or threw out of the rack: the runner catches it and sets status = -1 -> the whole engine
       (Csound + every VST) stops with "VST processing failed.",
   and because the reload was unloadAll + recreate EVERYTHING, every other track lost its plugin
   instance and its held voices too - the familiar "everything goes mute, delete the track and
   re-create it" symptom.
B) The fix - a loader thread, an instance registry, adopt-by-swap
   - VstRack now keeps an INSTANCE REGISTRY (insts_: track id -> loaded plugin) that outlives
     every graph. queueJobs() compares a load signature (id|path|kind). Same signature = wiring
     only (setWiring, as in Round 27). Different = the request goes to a background loader.
   - The loader thread (own COM apartment here; the old OleInitialize-only trick is now local to
     it) builds the new graph: it REUSES every instance whose (track, .vst3, kind) still matches
     and creates ONLY the new / changed plugin. Every create / load / parameter restore /
     prepare() is wrapped in try/catch: a failing plugin only drops its own track ("that track
     stays silent"), the previous graph keeps playing and the engine stays up.
   - Graphs are immutable shared_ptr snapshots. The loader publishes the finished graph; the
     audio thread adopts it at the top of a block with a pointer swap (no load, no destroy on
     the audio path). The old graph is retired to a graves list and destroyed by the LOADER
     thread - a plugin destructor can never run inside the callback.
   - The MIDI note ring continues across a rebuild: each instance carries the audio thread's
     read position (Inst::wr); a reused instance resumes there, a brand-new instance starts at
     the ring HEAD so notes it never saw are not re-fired.
   - Csound channels (P1..P8, wr, tab) are resolved lazily on the engine thread
     (resolveChans), never on the loader thread; a P slot picked while the engine runs resolves
     on the next block, and a live pick invalidates the cached pointers for that track only.
   - The rack's log lambda is now a mutex-protected relay drained by the engine thread (the
     console queue is single-producer SPSC), so loader-thread lines show up in order.
   - VstSoloEngine::start() no longer calls rack_.clear() on a signature change: rack init()
     reuses matching instances (the 4th engine gets the same "only the picked plugin is
     created" behaviour), and Stop / Run VST keeps holding the exact same instances.
   - Init's synchronous build is serialized with the loader (loaderLifeMutex_), so a wiring push
     that lands while a Run is loading plugins cannot build a second graph concurrently.
   - Console: "CAW engine build: 39_one_rack_28 (one VST graph in the engine; plugin changes load
     off the audio thread)."
C) What to look for when testing
   - While playing, pick / change a plugin: the transport keeps running, the other tracks keep
     sounding, and the console prints "[caw] VST graph reloaded live (no Run needed); every
     track kept its plugin instance." (plus one "VST track \"name\" loaded (...)" line for the
     picked plugin only).
   - Pick a plugin while stopped, then Run: same line set, no engine restart.
   - A plugin that fails to load prints "the plugin threw while loading ... - that track stays
     silent." and DOES NOT stop the other tracks or the engine.
   - Stop VST / Run VST and Stop / Run (Csound): no plugin is re-created (the "VST engine: the
     plugins stayed loaded" line still applies), held notes never replay.

Round 29 - Saved plugin state no longer mutes the VSTi (the "no sound unless I re-create the VSTi" root fix)
-------------------------------------------------------------------------------
A) Root cause
   Loading a project restored every stored parameter value into the plugin TWICE:
     1. IPlugin::setParam -> IEditController::setParamNormalized, once per saved value, and
     2. the same values were queued again as IParameterChanges for the FIRST ProcessData block
        (initialParameters_ replay, so the processor - not just the controller - learns them).
   A project stores the full parameter list (the reported project: ARP 2600 V3 track = 2360
   values, kHs Pitch Shifter track = 2087 values), so block 0 carried a few thousand parameter
   changes at sample offset 0. The ARP 2600 stops producing audio when it receives that many
   changes in one block; the whole project went silent, and every re-run restored the same state
   and silenced it again. A VSTi created fresh has no saved state, so it never took that path -
   which is exactly the reported asymmetry ("works when I create the VSTi after the VSTe, no
   sound otherwise").
   Headless check with the real plugins: with the project's saved state every scenario (replace,
   mix, instrument alone) measured master = 0.0000; with the replay disabled they all sounded
   again (master 0.37 / 0.52 / 0.40). Bisection showed the trigger is the NUMBER of restored
   values in one block (287 ok, 288 silent), not any single parameter - every saved value in that
   project equals the plugin's own default (0 of 2390 differ), so the silence came purely from
   the restore act.
B) The fix
   - Restore only values that actually differ from what the plugin reports after load
     (fabs(saved - current) > 1e-6), in both restore sites: VstRack's graph build (engine
     instance) and the VST panel's track-load restore (UI instance). Redundant edits are dropped,
     so a project whose patch is at the plugin defaults now restores nothing at all.
   - The initial-value replay is bounded to 128 parameter changes per block and continues on the
     following blocks (initialParameters_ entries are consumed as they are sent). Automation
     from the lane ring is still queued after the initials of the same block, so the lane value
     wins; a parameter that also has a pending initial value gets the initial first and the lane
     value last. Large custom patches (hundreds of non-default values) therefore load without
     ever flooding a plugin, verified with 361 and 501 real differences.
   - Console: "CAW engine build: 40_param_restore_29 ...".
C) What to look for when testing
   - Open the reported project (VSTi1 ARP 2600 V3 + VSTe2 Pitch Shifter in replace mode wired to
     VSTi1) and Run: the VSTi sounds immediately, the VSTe replaces its source with processed

   - Change a parameter in the plugin's own window, save, reload the project: only that value is
     restored (the others are left at the plugin's defaults).

Round 31 - VSTi into VSTe sounds "frozen / flanged feedback" (the picked parameter was pinned to 0)
   (Minimal fix on top of Round 29. The Round 30 "Run VST is the one host" attempt was rejected -
    its code was reverted and its notes were dropped from this file.)

A) Root cause
   - A VSTe clip's code sends P1..P8 to the plugin every block (chnset kP<k>, "cawvst_<id>_p<k>"),
     and P1..P8 are whichever parameters the user learned into those slots. The default code a new
     VSTe clip started with was:  P1 = clip(level(in) * 4, 0, 1)
   - level(in) reads the RMS of the clip's input audio (cawvstin_<id>_1/2), but nothing ever
     declared or wrote those channels, so the clip's aInL/aInR were silent locals and level(in)
     was ALWAYS exactly 0. Every block the clip therefore wrote P1 = 0.
   - In the reported project the first learned parameter is the Pitch Shifter's Pitch, so the
     effect's pitch was forced to 0 every block. Csound's chnset lands after the rack's own
     override pass for the block, so the 0 wins over the knob. Pitch = 0 in kHs Pitch Shifter is
     not a pass-through: it comb-filters / resamples the signal into the smeared metallic
     "freezing feedback" that was heard (real rack, ksmps 32: correlation 0.845 to the clean
     path, residual 0.534; same rack with nothing learned: correlation 1.000, residual 0.000).
   - The rack path itself was never at fault: VSTi -> VSTe at block size 32 through the real
     graph is bit-exact (correlation 1.0000, residual 0.000).

B) The fix
   - New default VSTe clip code touches no P slot; it explains that P1..P8 are the picked
     parameters and that driving one is optional (kVsteClipCode in src/app.cpp).
   - upgradeVsteDefaultClips() runs at project load and replaces the exact old default text in
     every VSTe track and clip code, so projects saved before the fix regenerate corrected
     Csound. Hand-written code never matches and is left untouched; VSTi code is never touched
     (a VSTi's P1 can be its note pitch).
   - The CSD declares cawvstin_<id>_1/2 for every VSTe, and the rack writes the packed input
     block into them every block, so `in` / `level(in)` in clip code carry the real input audio
     (one ksmps late, which is inaudible for a level follower).
   - level() is smoothed (port ..., 0.05): one ksmps of RMS is a spike, not a loudness.
   - Console: "CAW engine build: 41_vste_input_31 ...".
C) What to look for when testing
   - Open a project with VSTi1 ARP 2600 V3 + VSTe2 Pitch Shifter (replace, wired to VSTi1) and
     Run: the VSTe plays the VSTi through the effect cleanly - no frozen / feedback smear.
   - VSTe2's clips no longer contain "P1 = clip(level(in) * 4, 0, 1)" (upgraded on load); a Pitch

Round 32 - CSD and VST separated: the generated CSD contains no VST channels
-------------------------------------------------------------------------------
A) Why
   - Round 31 made `in` / `level(in)` real by printing chn_a "cawvstin_<id>_1/2" into the CSD.
     That works, but it puts VST-side routing inside the Csound project: the CSD (project text
     the user sees) declares a dependency on a host buffer it does not own, and WHICH buffer
     survives depends on declaration order versus the host's own csoundGetChannelPtr call.
   - Probe result: an audio channel created from C with
     csoundGetChannelPtr(cs, &p, name, CSOUND_AUDIO_CHANNEL | CSOUND_INPUT_CHANNEL |
     CSOUND_OUTPUT_CHANNEL) BEFORE csoundCompile returns the SAME pointer before and after the
     compile, and a Csound clip's chnget of that name reads it (rms converges to 0.496507 for a
     0.5 constant). The CSD therefore needs no channel declaration at all.

B) The fix
   - src/csd_builder.cpp no longer emits chn_a cawvstin_*; a comment records that the engine
     creates them. The CSD still carries chn_k cawvst_<id>_wr/_tab/_p1..8 (control side, shared
     with the clip code) - only the VST audio channels moved out.
   - src/csound_api_runner.cpp: ensureVstInChannels() creates cawvstin_<id>_1/2 for every
     non-instrument VST job from C (flags 2|16|32) before the CSD compiles (right after
     createMessages) and again when a live graph push adds a VSTe (setVstJobs / setVstWiring set
     vstInChDirty; the block loop drains it). vstInChMade is per Csound instance (cleared at
     engine start); a failed creation is logged once. The rack still writes the packed input
     block into those buffers every block, so `in` / `level(in)` keep working unchanged.
   - Console: "CAW engine build: 42_vste_nocsd_33 ...".

   Ported from the 43_startup_5_good files:
   - app.cpp: trackIsVst() (kind 3 OR 4) - an effect's parameters, picks and live values now reach
     the standalone 4th engine too (trackIsVsti only covered instruments).
   - vst_rack.h: a pick with no Csound lane (standalone engine) falls back to the pick's start
     value instead of being skipped; one-shot logs for "VSTe NOT active - skipped, source plays
     dry", "input names a VST source that is NOT in the rack - press Run once", and a first-run
     per-VSTe state line (routedIn, packedLines, input peak, output peak, per-source state).
   - vst_ui.h: picking a VSTe input source turns the row ON and pushes the live input mask.

   NOT ported, deliberately:
   - "Insert-safety" (put the dry source back when no effect produced finite non-zero output this
     block). It makes the replace decision depend on audio content, so any effect that is silent
     at a block boundary (attack, latency, an empty arp step) gets its dry source added on top of
     the wet path. Measured at block 32 through the real rack: corr(arp) 1.000 / residual 0.000
     without the block, 0.965 / 0.263 with it, unchanged by the cawvstin rows. An effect that is
     muted / not soloed already cannot replace its source (it is skipped and says so), and the
     new first-run diagnostics name a plugin whose output is silent - routing itself stays exact.

     send them all at once): that is what silenced the ARP 2600. Different-only restore and the
     128-changes-per-block replay are kept.

Round 33 - One plugin per VST3 class id: multi-plugin bundles, the Settings VST3 browser, editors
-------------------------------------------------------------------------------------------------
A) Why
   - A .vst3 bundle is a container. Its identity is (file, class id): one file can expose several
     plugins (Arturia / Kilohearts bundles), and CAW only ever loaded the FIRST audio class it
     found (it stopped at the first kVstAudioEffectClass in load()). Picking another plugin from
     the same company therefore reopened the same bundle and loaded the same first class again -
     it looked like "selecting does nothing"; picking a plugin from another company changed the
     file, which is why that appeared to "fix" it.
     The path was also the identity everywhere else: the scanner stored one name per file, the
     picker rows were keyed by path, the track saved only vstPath, the rack reused instances by
     path, the solo-engine signature and the live-reload check compared paths.
   - Kilohearts editors (Phase Plant, Snap Heap - the animated GUIs) and some EQs mis-size or draw
     broken when IPlugViewContentScaleSupport::setContentScaleFactor arrives AFTER attached();
     CAW did exactly that (scale was applied in resizeEditor/showEditor after attached). JUCE hit
     the same plugin behaviour and documented calling the scale first. A second call with the same
     factor also makes some editors (TBProAudio) apply their display scale twice.
   - There was no way to point CAW at a VST3 folder that is not one of the four system folders
     (portable installs, per-user folders), and no visible way to rescan.

B) The fix
   - Identity = (path, class id) end to end.
     src/plugin_host.h: IPlugin::load(path, classId, err) + classId() (the class actually loaded);
     PluginInfo carries classId; vst3ExtraDirs()/setVst3ExtraDirs() persist user folders.
     src/vst3_host.cpp: cidText()/normCid() (canonical 32 uppercase hex, accepts braces/dashes/
     lower case); load() picks the class whose CID matches (empty id = first audio class, old
     projects), refuses a missing class with "this .vst3 does not contain the selected plugin
     class", and pins classId_. scanVst3Info() cache v3 stores ONE LINE PER CLASS and replays every
     class of an unchanged bundle. User folders live in <home>/.caw_vst3_dirs.
     src/model.h vstClassId, src/vst_job.h classId, src/project_io.cpp CAW_PROJECT 54 + a VSTCID1
     block (one string per track, written/read for all tracks).
     src/vst_rack.h: reuse only when (track, path, classId) all match; loadSig includes the class.
     src/vst_solo.h: solo signature includes the class. src/app.cpp: collectVstJobs passes it.
     src/vst_ui.h: Slot.loadedClassId; niceName(path, classId) names the exact class (a file-level
     name when no class is chosen); picker rows are keyed by path+class id (one row per plugin,
     not per file); picking calls loadPlugin(path, classId); the track is pinned to the class the
     plugin reported; parameter mapping carry-over respects the class too.
   - Editor attach: setEditorScale(windowDpi(hwnd)) now runs BEFORE attached(), identical factors
     are skipped (lastScale_), and after attached() an explicit onSize with the final client rect
     runs (many GUIs start their layout/animation timers there). IPlugin::closeEditor() +
     a panel button "Reopen editor" destroy and recreate the window without reloading the
     plugin (the DPI-mode switch uses it too, instead of a full plugin reload).
   - Settings > Programs > VST3 PLUGINS: "Scan VST3 plugins" (restart the scan), "Add folder..."
     (plat::chooseFolder, persisted, rescans), the list of added folders with Remove, the number
     of plugin classes found. The scanner also reads the added folders.

C) What to look for when testing
   - Two plugins from one bundle (Arturia/Kilohearts): pick the second one - it loads; pick it

Round 34 - Changing a plugin no longer inherits the previous plugin's values (same-vendor switch)
------------------------------------------------------------------------------------------------
A) Why
   - Plugins from one vendor reuse one parameter-id space. Measured on the installed plugins:
     Arturia DX7 V -> Mini V4: 2663 of 2663 ids of B exist in A (100.0%); Kilohearts Slice EQ ->
     Phase Plant: 2090 of 2174 (96.1%). CAW keyed the saved patch by parameter id
     (Track::vstParameterState), captured EVERY writable parameter of the outgoing plugin into it,
     and after loading the next plugin replayed the map id by id - in the editor copy AND, through
     VstJob::parameterState, in the engine instance.
     Measured effect (probe h19, DX7 V values replayed into Mini V4): 2605 values applied, 2589 of
     Mini V4's 2663 controls left their own defaults after the load - the editor opened showing
     another instrument's settings, and an instrument whose oscillator/filter/envelope ids were
     overwritten that way makes no sound ("VSTi does not work when changing"). Kilohearts: 2090
     values replayed into Phase Plant the same way.
     The known-good 38_bridge_19 build cleared that map whenever the file changed, which is why
     picking a plugin from another company "fixed" the next pick from the same company. Round 33
     introduced class ids but kept the replay.
   - Round 33 also moved IPlugViewContentScaleSupport::setContentScaleFactor BEFORE attached().
     The build the user pointed at (38_bridge_19_fixed17) sizes the window from getSize() before
     attached(), applies the scale AFTER attached() and then re-queries getSize() so the plugin's
     own (scaled) size reaches it as onSize. Kilohearts returns kResultOk to the pre-attach scale
     call but lays the GUI out on the post-attach size, so the earlier call changed nothing.

B) The fix
   - src/vst_ui.h: loadPlugin() now decides "this is a different plugin" from (path, class id),
     not the path alone, and clears Track::vstParameterState BEFORE the load when it is. The
     restore loop then finds nothing and the plugin opens on its own defaults; the engine's copy
     gets the same empty map through collectVstJobs, so both sides agree. Re-picking the same
     (path, class) - and opening an old project, whose class id is empty until first load - still
     restores the saved patch.
   - src/vst3_host.cpp: showEditor() follows the reference order - getSize + resizeEditor before
     attached(), applyEditorScale after attached() (setContentScaleFactor, then the view's own
     getSize + onSize), plus the explicit onSize with the final client rect. setEditorScale() now
     records a factor as applied only when the plugin returned kResultOk, so a refused scale is
     retried by the next resize instead of being deduplicated away.

C) What to look for when testing
   - VSTi: with one Arturia (or Kilohearts) plugin playing, pick another from the same company -
     it loads, its editor opens on ITS default patch (sliders/kb at their own positions, not the
     previous plugin's), and it sounds. Pick the first one again: still works, no reload needed.
     Switching between companies keeps working. A saved project still reopens its plugin with
     the patch it was saved with.
   - Kilohearts Phase Plant / Snap Heap: open the editor right after loading it fresh - the
     window is sized by the plugin and the animated elements move. If a specific editor still
     draws wrong, "Reopen editor" reattaches it (size, then scale) without touching the patch;
     the "Windows compatibility scaling" box + Apply switches DPI mode the same way.
   - caw_vst_log.txt: every open shows "editor: attach", "editor: client <w>x<h>",
     "editor: mode=native|windows ... scale <factor> -> <tresult>", "editor: attached, scale ...,
     size ..." in that order (size first, scale after attach).
