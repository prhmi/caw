======================================================

Round 3 fixes (on top of round 2). This round I went through the whole engine pipeline line by
line: how the VST tracks are generated into the Csound project, and the complete audio routing
map of every engine (Csound clips, Pure Data, SuperCollider, VSTi, VSTe).

THE AUDIO ROUTING MAP (what actually happens per block)
-------------------------------------------------------
One Csound block on the engine thread:
  1. Csound runs one block. Csound clip audio goes to the master (spout) AND to the meter taps
     (gaCawT_<clip>_<ch>). For every VSTe input route the taps are chnmixed into the audio
     channels cawvstin_<vstTrackId>_<line>  (CSD, fixed at Run time).
  2. The drain writes one-shot UI values into named control channels (cawvst_<id>_p<k> and the
     clip lane channels).
  3. The VST rack runs every VSTi/VSTe plugin: it reads kP1..kP8 + the packed input lines, runs
     the plugin, and ADDS the plugin output into the master (spout).
  4. Pure Data renders (pd->render) and its output is ADDED INTO THE MASTER AFTER THE RACK.
  5. SuperCollider renders inside CAW's audio callback (PortAudio) - completely outside the
     engine thread - and its output is added to the device stream last.

THE TWO ROOT CAUSES I FOUND THIS ROUND
--------------------------------------
a) Parameters: the whole chain (UI -> setControlChannels -> drain -> Csound channel -> rack ->
   ParamMsg -> plugin) is correct, but every hop is INDIRECT. If any single hop fails or is
   overwritten (clip not running, clip overwriting the channel, automation, a channel that could
   not be resolved), the change never sticks and only a restart (which loads the saved parameter
   state directly) applies it. There was NO guaranteed same-block path.
b) Pure Data / SuperCollider: their audio NEVER passes through Csound or the rack (see steps 4
   and 5 above). A VSTe input sourced from a PD or SC track got silence - restart did not help
   either, because the routing only ever carried Csound-side audio. That is the "for pd and
   super not at all".

ROUND 3 CHANGES
---------------
1. Guaranteed live parameters - a DIRECT override path
   The panel now also pushes every parameter change straight into the rack
   (VstRack::pushParamOverride, UI -> CsoundApiRunner::pushVstParamOverride). The rack applies it
   on the VERY block it arrives: no Csound channel involved, nothing can delay or revert it.
   Rule in the rack: the manual value wins; it releases as soon as the channel value catches up
   (no automation - the value sticks), or when automation actively moves the lane after a 500 ms
   window (automation resumes, like touching a param in a DAW). While the lane is static but
   cannot carry the value, the manual value simply holds.
   The channel writes from round 2 stay in place (engine channel + every clip's lane channel) so
   the value also persists for the running clips and the next Run. The editor-GUI <-> engine
   mirror from round 2 is unchanged.
   This works for BOTH VSTi and VSTe tracks and no longer depends on any clip state.

2. Pure Data and SuperCollider sources now feed VSTe inputs
   - A track / clips input whose source is a PD (kind 6) or SC (kind 5) track reserves two stereo
     lines and feeds the WHOLE engine mix into the slot (VstJob::Input.engine = 1 / 2). A PD / SC
     mix cannot be split per clip - the mix of that engine is the source.
   - PD: the engine publishes the latest pd->render buffer to the rack each block
     (VstEngineAudio.pdMix). SC: CAW's audio callback captures the SC mix into a lock-free ring
     (CawScRing) and the rack pulls one block per block (VstEngineAudio.scRing).
   - If an ACTIVE master-mode VSTe consumes the mix, the RAW mix is suppressed while it runs:
     PD inside the engine thread, SC via an atomic flag checked in CAW's audio callback. The
     processed output replaces the raw mix (master semantics). With mix-mode VSTe tracks both
     play in parallel.
   - Master (mode 2) inputs still read the Csound master spout - note that spout contains
     Csound + VST output; the PD mix is added after the rack, so a "master" input does not
     include PD (use a PD track input for that). SC is added in the audio callback and is also
     not in the spout.

3. Audio inputs UI (your requests)
   - Unchecking an input does NOT hide the row anymore: the row stays, greyed state, audio off.
   - A separate small "-" button per row collapses the row (UI only); "Show hidden" brings all
     collapsed rows back; hidden rows keep their settings.
   - The name text box is shorter (fixed 120px-scaled width instead of filling the whole row).
   - "+ Add input" adds the next unused slot; the counter shows configured / 8.

ROUND 4 — THE BUG THAT KEPT TRACK / CLIPS INPUTS SILENT (fixed here)
--------------------------------------------------------------------
You tested fixed3 and track/clips inputs still produced nothing. I re-read the rack line by line
and found the ordering bug, plus one smaller stride bug:

1. THE SILENCE BUG (vst_rack.h) - the rack CLEARED the cawvstin_<id>_<line> channels at the TOP
   of the per-track loop, BEFORE reading them into the plugin input buffer. The timeline in the
   engine loop is: Csound perform() runs first (the clips chnmix this block's audio into the
   cawvstin channels), THEN the rack runs. So the clear destroyed exactly the block Csound had
   just written, and rdAt() then read zeros - on EVERY block, for EVERY track/clips input. The
   audio path was correct everywhere else (CSD taps, chnmix, line ranges, packing, plugin
   channels); it was erased in the last step before the plugin. Master inputs were unaffected
   (they read the spout, not these channels), and parameters worked, which matches "still dont
   work" for track/clips sources only.
   FIX: the channels are now cleared AFTER the per-track loop (for every routed VSTe, active or
   muted, so they can never accumulate), i.e. read -> run plugin -> clear, and the next perform()
   mixes into fresh channels again.

2. PD MIX STRIDE (csound_api_runner.cpp) - VstEngineAudio.pdMixChannels was never set, so it
   stayed at the default 2 while the PD mixer actually renders interleaved at the engine channel
   count (prepare uses nchan). With a 2-channel soundcard setup it worked by luck; with 4/6/8
   channels a "PureData" input read the wrong stride (garbage / half-rate audio).
   FIX: vstEa.pdMixChannels = (int)nchan is now set when the rack is prepared.

Verified in the sandbox: vst_rack.h compiles clean in BOTH build variants (with and without
CAW_VST3) via g++ -fsyntax-only; the runner change is a one-line in-scope assignment. Still not
a full build (no VST3 SDK / ImGui / cmake / portaudio here) - build with build.bat.

What to expect after rebuild (38_bridge_19_fixed4):

ROUND 6 — LIVE PARAMETER EDITING REBUILT (the actual feature)
-------------------------------------------------------------
You told us what it is really about: LIVE PARAMETER EDITING. I read the whole chain - the
plugin wrapper, the VSTE panel sync, the runner queues, the rack - and found the structural
bug plus several holes. This round rebuilds the live path so an edit ALWAYS reaches the
running engine and leaves proof in the console.

THE STRUCTURAL BUG (vst3_host.cpp) - EDITOR KNOB TURNS WERE THROWN AWAY
  When you turned a knob in the plugin's OWN window, VST3 sends the value to the host via
  performEdit. The wrapper's EditorHandler::performEdit DISCARDED the value (it was not even
  read - only the Learn feature recorded that a knob moved). The live sync
  (syncLiveParameters, every frame) compares the plugin's value against the last agreed value
  to detect YOUR edit - but the value never updated, so it never pushed anything to the
  engine. Turning knobs in the plugin's own window could never work, in any round.
  FIX: performEdit now captures the value and updates the parameter cache immediately
  (handler_.onLiveEdit). A knob turn is detected on the next frame and pushed to the engine.

WHAT ELSE WAS FIXED / HARDENED
1. getParam (vst3_host.cpp) already polls the plugin controller directly, so editor state is
   authoritative; the new performEdit capture closes the last gap (plugins whose editors
   bypass performEdit still update the cache through the controller poll).
2. The rack now holds a live edit for 2.5 s (was 0.5 s), refreshed on every drag event - a
   quick tweak no longer snaps back while running automation catches up (vst_rack.h).
3. The GUI no longer fights your hand: while the mouse button is held anywhere, the engine
   mirror never drags the editor knobs back (vst_ui.h).
4. Re-picking parameters WHILE RUNNING now works: the P1..P8 mapping is queued to the rack
   (pushVstPickRefresh -> CsoundApiRunner::refreshVstPicks -> VstRack::pushPickUpdate) and the
   next edit maps to the right parameter without restarting (vst_ui.h, csound_api_runner.h/.cpp,
   vst_rack.h). Previously a slot picked after Run silently pushed to the WRONG parameter.
5. PROOF IN THE CONSOLE - every applied live edit logs one line:
     [caw] live param: "MyTrack" P2 -> 0.800

     [caw] live param: "MyTrack" P2 released (lane automation took over)
   If you drag a slider and see NO "live param" line, the edit did not reach the engine -
   copy the console and we know exactly which link is missing.
6. If the build has no VST3 host (CAW_VST3=OFF), the engine says so at startup and the VST
   panel shows a red banner - no more silent dead panels.

THE COMPLETE LIVE PATH NOW (all links verified)

ROUND 11 — VSTi AS A TRUE 4TH ENGINE (DAW-LIKE)
------------------------------------------------
The VST rack already IS a 4th engine: the plugins render next to Csound / PD / SC
on the engine thread and their audio is added straight to the soundcard mix -
nothing of a VSTi runs through the Csound orchestra. What still tied it to the
Csound world were the NOTES, and that is what this round removes.

1. WHY A VSTi STAYED SILENT EVEN WITH A MIDI CLIP (the bug):
   MIDI clips only played when they could BORROW a code clip: the note events
   fired the code clip's instrument, which re-fired the note helper. A muted,
   deleted or missing code clip silently dropped every note. And "Add MIDI clip"
   existed only in the CLIP right-click menu, so a MIDI clip without a code clip
   was easy to build and could never sound.

2. MIDI clips on a VSTi track now send notes DIRECTLY to the plugin:
   every note is one score event on CawVstNote_<id> (on at note start, off at
   note end). No code clip involved anywhere - mute or delete the code clip, the
   MIDI clip still plays. A VSTi now behaves like a DAW instrument:
     Add VSTi -> load plugin -> right-click the track > Add MIDI clip ->
     draw notes in the MIDI editor -> Play. Sound.
   Csound tracks keep the old borrow behaviour (the notes play the clip's
   instrument); PD / SC tracks are untouched.

3. "Add MIDI clip" is now also in the TRACK right-click menu (VSTi tracks):
   creates a silent code clip plus a 4-second MIDI clip at the playhead in one
   step. The code clip holds only a comment - the notes come from the MIDI clip,
   so the template's random-note code cannot double-trigger.

4. The AUDIO OUTPUT (Master replace / Mix) option is hidden for VSTi tracks:
   it only makes sense for an effect. An instrument always sends its audio to

ROUND 12 — THE LIVE-PLAY NOTE DROP (why a VSTi stayed silent even with fixed11)
-------------------------------------------------------------------------------
The console in the screenshot ("instr VSTi1 uses 5 p-fields but is given 6" +

ROUND 17 - LIVE CODE EDITING
----------------------------
Editing the code of a VSTi / VSTe clip (or a Csound clip) no longer needs a Run / restart: the
engine recompiles that clip's instrument while it plays.

- When the code editor of a clip stops changing for 0.5 s, the clip's instrument definition is
  pushed to the running API engine (csoundCompileOrc between audio blocks), using the exact text
  the Run CSD would contain (buildClipInstrumentCode cuts it out of buildCsd "engine"), so a later
  full restart never recompiles a different definition.
- The clip is then restarted (same rules as Run: playing timeline / manual run, M / S respected)
  so the new code is heard; other clips and engines are untouched, their live P1..P8 overrides
  and automation survive. The edited clip's P values re-init from its defaults.
- Csound 6 (csoundCompileOrc(cs, text)) and Csound 7 (extra async argument) are both handled; an
  engine without the runtime compiler says so once in the console instead of failing silently.
- Audio-rate / control-rate instruments keep their running instance's state otherwise; notes sent
  from MIDI clips follow the usual transport. PD / SC tracks keep their own live reload.
- Console: "[caw] live code "<clip>": recompiled" or the compile error, per push.
Files: csd_builder.h/.cpp (buildClipInstrumentCode), csound_api_runner.h/.cpp (compile queue +
pushLiveInstrument), app.cpp (edit detection, push + single-clip restart).

ROUND 18 - RUN VST PLAYS THE CLIP CODE BY ITSELF
------------------------------------------------
Before, clip-code notes (note / cc / msg) only reached the instruments through Csound: Run VST
loaded the plugins and played the MIDI clips, but a clip that says "every 0.5 { note ... }"
stayed silent unless Csound was running too.

Now the VST engine interprets the CAW code itself while Csound is OFF:
- new src/vst_script.h: parser + runtime for the language documented in vst_lang.h - every /
  when / else, note / cc / msg, P1..P8 (read, write, +=), own variables, ternary and the math
  set (lfo / tri / sqr / saw, rnd, smooth, line, clip, min / max, abs / sin / cos / int / sqrt,
  mtof, uni), pitch / vel / dur / time / pi.
- vst_solo.h: the engine evaluates each VSTi clip's code once per 128-sample block on its own
  transport clock, inside the clip's box, with loops / seeks / Play / Stop. `note` starts a
  note that ends after its length (same active-note list as the MIDI clips); `cc` / `msg` go
  straight to the plugin; a P1..P8 the code writes is pushed into the plugin as a live
  parameter. Clip-code edits recompile the running engine after the usual 0.5 s pause.
- app.cpp: builds the scripts from the VSTi tracks (respects track / clip mute and solo) and
  hands them to the engine only while Csound is off. As soon as Csound runs again the list is
  cleared, because Csound translates the same code and forwards its notes - never both.
- `csound:` lines, plain Csound statements and level() have no meaning here and are ignored
  (they still work when Csound is the one running the code).
No restart of any engine is needed. Press Run VST, then Play.
Files: vst_script.h (new), vst_solo.h, app.cpp.
